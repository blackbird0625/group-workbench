# 小组作业工作台 · Group Workbench

> 让每项任务有负责人、每次交付有证据、每次返工有原因。
>
> 面向中国高校小组作业的协作与过程监管工具：减少“假装在做的”，也别让真正干活的人一直替别人收尾。

## 为什么需要它？

聊天群里最热闹的，不一定是干活最多的；一句“我负责这部分”，也不等于最后真的有交付。

Group Workbench 把任务、负责人、截止时间、交付物、审核意见和文档版本放到同一个工作台。**它不是靠组长反复催问，而是靠流程把责任摆到明面上：**

- **谁认领了任务，系统就记录谁负责**，不再只有口头承诺。
- **没有附件或文档版本，不能提交审核**，“做完了”必须拿得出成果。
- **状态不能随意跳变**，任务必须沿“认领 → 执行 → 审核 → 验收”推进。
- **返工必须写明意见**，负责人知道改什么，管理员也能复盘问题。
- **文档保存版本、编辑者和时间**，贡献有依据，修改可回看。
- **匿名访问看不到组内业务数据**，任务和交付物不再对未登录访客公开。

## 针对“不负责任队友”的监管设计

| 常见问题 | 工作台怎么约束 | 组长能看到什么 |
|---|---|---|
| 一直不领任务 | 任务先进入待认领，负责人和状态清晰展示 | 哪些任务没人接、是否临近 DDL |
| 认领后长期没动静 | 认领即绑定负责人，进行中任务持续展示 | 谁占着任务、任务停在哪个阶段 |
| 嘴上说完成，实际没成果 | 没有附件或文档版本就拒绝提交审核 | 交付物是否真实存在 |
| 绕过审核直接标完成 | 服务端严格校验状态流转和验收权限 | 任务必须按规定路径完成 |
| 被要求返工却说不知道原因 | 返工意见必填，并写入任务评论 | 谁提出返工、具体要改什么 |
| 文档改了却说不清谁做的 | 每次有效保存形成版本，记录编辑者与时间 | 各版本内容、贡献者和提交记录 |
| 非负责人替别人提交 | 提交审核、返工恢复等操作校验负责人身份 | 关键操作由有权限的人完成 |
| 未登录也能围观全部内容 | 匿名接口只返回登录页所需摘要 | 组内任务和资料只向有效会话开放 |

> 这里的“监管”是让协作过程透明、责任明确，不是隐蔽监控。所有成员应知道平台会记录哪些协作信息；不要用工作台收集与任务无关的个人数据。

## 核心工作流

```text
待认领 → 进行中 → 待审核 → 已完成
              ↑       │
              └──── 需返工
```

实际规则如下：

1. **认领**：成员认领待认领任务，系统自动写入负责人。
2. **执行**：负责人编辑交付文档、上传附件，并在任务内沟通。
3. **提交审核**：必须先有至少一个附件或文档版本；非负责人不能代为提交。
4. **审核**：有权限的管理员可以验收通过，或填写意见后退回返工。
5. **返工恢复**：负责人根据明确意见继续修改，再重新提交审核。
6. **留痕**：认领、状态变化和返工意见写入任务记录；文档保留版本历史。

这套流程同时保护组长和组员：组长不用凭印象分工，组员的真实贡献也不会被一句“都是大家一起做的”抹掉。

## 功能一览

| 模块 | 能力 | 可关闭 |
|---|---|---|
| 总览 | 我的任务、待认领、待处理意见、最新公告 | 核心 |
| 任务看板 | 负责人、DDL、五状态流转、任务评论、附件 | 核心 |
| 交付文档 | Markdown、版本历史、编辑者记录、选中文字批注 | 核心 |
| 审议与验收 | 提交审核、返工意见、验收权限控制 | 核心流程 |
| 资料库 | 分类上传文件，单文件限 6 MB；大文件可放网盘链接 | ✅ |
| 公告区 | 发布公告、重要公告置顶 | ✅ |
| 文献汇总 | 题目查重、投票、审稿评论、采纳后导出清单 | ✅ |
| 审议意见 | 对任务安排提建议，管理员标注采纳或不采纳 | ✅ |
| 提醒 | DDL、周日进度、管理员待办提醒 | 内置 |
| 备份恢复 | 全量 JSON 备份与恢复，包含附件 | 管理员 |

其他能力：每 12 秒多设备自动同步；模块、任务分类、资料分类和权限规则均可配置。

## 快速开始

要求：**Node.js 18 或更高版本**。默认本地文件存储，无需安装第三方依赖。

```bash
git clone https://github.com/blackbird0625/group-workbench.git
cd group-workbench
npm start
```

浏览器打开 **http://localhost:3000**。首次启动会进入初始化向导：

1. 从服务端启动窗口复制**初始化密钥**，填入向导第一步。
2. 配置名称、功能模块、权限、任务分类和资料分类。
3. 填写成员名单并指定管理员。
4. 每位成员首次登录时设置自己的 PIN。

初始化密钥可通过 `SETUP_KEY` 环境变量提前指定；未指定时由服务端随机生成。**不要把它发到组员群或提交进仓库。** 初始化只允许成功一次。

运行回归测试：

```bash
npm test
```

## 权限与初始化

初始化向导共 6 步：

1. **基本信息**：初始化密钥、工作台名称、副标题、管理员称呼。
2. **功能模块**：选择资料库、公告区、文献汇总、审议意见等模块。
3. **权限设置**：决定新建任务、分配任务、验收、发布公告等操作的权限。
4. **任务分类**：自定义看板分类。
5. **资料分类**：自定义资料库分类。
6. **成员与管理员**：维护成员名单，支持多管理员。

提供“组长集权 / 民主协作 / 高度自治”等预设，也可以逐项调整。初始化配置保存在服务端，跟随工作台数据备份。

PIN 由成员本人设置，管理员可以重置但不能查看。身份认证不是装饰：服务端会校验关键操作，不能只靠修改前端页面绕过。

## 部署与数据

- **同一 WiFi**：组员访问 `http://你的IP:3000`，并在防火墙放行端口。
- **长期在线**：推荐 Render + Supabase，详细步骤见 [DEPLOY.md](./DEPLOY.md)。
- **默认存储**：`data/state.json`，运行时自动创建，已被 `.gitignore` 排除。
- **云存储**：设置 `STORAGE=supabase` 并配置相应环境变量。
- **备份**：管理员登录后使用右上角备份功能，定期下载 JSON 文件妥善保存。

部署前请阅读 [DEPLOY.md](./DEPLOY.md)，接口细节见 [API.md](./API.md)，本次安全与流程修复见 [CHANGELOG.md](./CHANGELOG.md)。

## 安全边界与已知限制

- 适合小组内部协作，不是高流量公众平台；当前登录接口**没有失败限流**，公网部署前应增加限流或接入反向代理。
- PIN 用于组内身份认证，请勿复用重要账号密码，也不要使用 `1234` 等常见组合。
- 过程记录用于协作追踪，**不是不可篡改的审计日志**；拥有服务器或数据库权限的人仍能修改底层数据。
- 请单进程运行。`server.js` 在内存中合并并延迟写盘，不要使用 pm2 cluster 等多进程模式，以免互相覆盖数据。
- 免费云平台的本地磁盘通常是临时存储；长期使用请配置 Supabase，并坚持备份。
- 附件以 base64 保存，单文件限 6 MB；数据量较大时应改用对象存储。
